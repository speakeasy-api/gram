# RBAC decision log

Decisions taken while reworking authorization that a reviewer did not settle in advance. Each entry says what was decided, why, and how to reverse it. Pull requests repeat their entries under "Decisions made without reviewer input".

## Scope catalogue

- **One entry type for presentation and rules.** `ScopeEntry` in `server/internal/authz/catalog.go` now holds a scope's evaluation rules (visibility, grant surface, satisfying scopes, exception scope, resource kind) beside its label and description. `ResourceType` was already exported and stays so; `visibility`, `surface`, `satisfiedBy` and `blockedBy` are unexported, so only the authz package reads them. Callers keep the exported fields they used before. A separate `ScopeDef` type was not added: it would have meant two types describing one scope.
- **Per-scope lookups are methods on `Scope`, backed by one index.** The separate expansion, exclusion, visibility, grant-surface and resource-kind maps are gone, and so are `ExclusionScopeFor`, `ScopeVisibilityFor`, `GrantSurfaceForScope`, `ResourceKindForScope`, `CalculateSubScopes` and `ScopeImplicationClosure`. Callers use `scope.BlockedBy()`, `Visibility()`, `GrantSurface()`, `ResourceKind()`, `SubScopes()` and `ImpliedScopes()`, which read a single `scopeIndex` built from `scopeDefinitions` (the catalogue plus `rootScopeEntry`). `scopes.go` keeps only the `Scope` type, its constants and `Parts`.
- **Root is defined beside the catalogue, not in it.** `rootScopeEntry` is registered so stored root grants evaluate, but it is never listed or described.
- **Unregistered scope names keep their prefix-based resource kind.** `Scope.ResourceKind` reads the catalogue first and falls back to the old prefix switch, so names the catalogue does not define (such as the retired `remote-mcp:*` family) answer as before.
- **Role defaults are a field on each entry** (`defaultRoles`), replacing the `adminScopes` and `memberScopes` lists. This reverses the plan's "role-keyed table" note at the reviewer's request. `SystemRoleScopes(role)` lists them in catalogue order, so `SystemRoleGrants` now lists grants in catalogue order rather than the old lists' order; the set each role holds is unchanged and pinned by the golden tables. Agent runtime eligibility stays in `runtimepolicy` until its own follow-up.
- **Required check context is not part of this change.** The plan's per-scope `Selectors` and `Requires` fields, and log-only diagnostics for malformed legacy checks, change what the engine logs. They come in a separate pull request so this one stays a pure refactor pinned by the golden tables.
