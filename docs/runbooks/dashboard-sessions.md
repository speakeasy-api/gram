# Dashboard session cutover (DNO-1035)

## Contract and security boundaries

- Access credentials have a fixed **10-minute maximum lifetime**. Every successful refresh issues a **new** access credential with a new 10-minute window; it never extends any older credential's expiry. Successful API calls and auth info reads do not extend expiry either. Support-session deadlines can shorten these windows.
- Both ordinary OIDC login and the Magic Auth invitation callback attach refresh state and set the scoped refresh cookie. An access-only invitation login is not sufficient for dashboard bootstrap.
- `Gram-Session` carries an access credential. The host-only, Secure, HttpOnly `gram_session` cookie remains a short-lived compatibility transport at `Path=/`, `SameSite=Lax`. It is not a refresh credential. Ordinary session middleware never renews it.
- The refresh credential is an opaque secret stored in two `gram_refresh` cookies containing the same value, at the exact paths `/rpc/auth.refresh` and `/rpc/auth.logout`. Both have **no Domain attribute**, `Secure`, `HttpOnly`, and `SameSite=Strict`. Only a digest is persisted server-side. Its idle window is 72 hours, capped by any support deadline. Separate paths are necessary because cookie path matching is slash-delimited: `/rpc/auth` does not match either dotted RPC name. Neither cookie is sent to ordinary RPC or chat endpoints.
- `POST /rpc/auth.refresh`, with the cookie and the exact configured dashboard `Origin`, returns **204**, an empty body, and the access credential in `Gram-Session`. The response must not be cached. The refresh secret must never appear in JSON, JavaScript storage, a URL, an access header, or telemetry.
- `POST /rpc/auth.logout` returns **200** through the existing SDK contract. Browser logout requires the same exact Origin validation and its endpoint-scoped refresh cookie, including when access has expired. It revokes refresh state, deletes the current access record, and clears both refresh-cookie paths and the access cookie. Valid header-only clients can continue to log out without a browser refresh cookie.
- Cookie paths reduce accidental credential transmission; they are not authorization or CSRF boundaries. The endpoint's exact Origin check is mandatory. CORS alone is not CSRF protection.

## Cutover and rollback

1. Both auth methods use the established `/rpc` ingress route. No infrastructure change or separate deployment is required.
2. Do not cache either auth endpoint, strip `Set-Cookie`/`Gram-Session`, or rewrite cookie Path/Domain/SameSite attributes at the proxy. Keep callback `/rpc/auth.callback` on the same browser-visible host used for refresh.
3. Deploy the backend and dashboard as a coordinated authentication cutover. New access records use the `sessions:v3:` namespace (plus the cache's deployment suffix); legacy namespaces are intentionally not read. **Existing dashboard sessions must sign in again.** Old open tabs should fail closed and reload/sign in rather than repeatedly retry mutations.
4. Do not copy or backfill legacy sessions into the new namespace. Let unreachable keys expire or remove only the specifically identified old namespace with an approved, environment-scoped procedure; never flush shared Redis.
5. Mixed old/new backend replicas can disagree about sessions during rollout. Drain old replicas and verify all serving replicas use the new namespace before declaring completion. Do not diagnose this by logging credential values.
6. A rollback to old code may make retained legacy keys valid again and restore sliding access expiry. Treat rollback as another authentication cutover: invalidate the old namespace before admitting traffic, or roll forward with a security-preserving fix.

## Refresh families, logout, and retained records

Each refresh issues a new access credential, preserving every older access record's original expiry. Refreshing a still-live token must not extend that token's lifetime.

For refresh-backed access, normal `GetSession` authentication checks the refresh family and takes current scope from its authoritative state. Older tabs can use their unexpired access credentials without restoring stale organization or support scope. A missing/revoked family denies **all related access credentials immediately for new requests**, even if their individual Redis records still exist.

Logout revokes the family, deletes its current access record, clears browser cookies, and deletes an explicitly supplied current access token. Older related records can remain **stored but unusable** until their original expiry, at most 10 minutes after issuance. The residual record lifetime is not a post-logout authorization grace period. Initial header-only access sessions without a refresh family still have a fixed 10-minute maximum lifetime; explicitly supplied current access is deleted on logout.

These guarantees apply to authenticating **new requests**, not to work or streams already admitted. An established stream remains admitted until it ends; token expiry or family revocation does not retroactively cancel it. Closing every established stream immediately would require separate cancellation/revalidation machinery. Clear client access state, abort client-owned streams on logout, and authenticate new connections through the family-aware check.

## Origins and cookie routing

The checked-in deployment configuration in **gram-infra**, not this repository's unrelated `infra/` package, sets matching `GRAM_SITE_URL` and `GRAM_SERVER_URL`:

- Production: `https://app.getgram.ai` (`values-prod.yaml`).
- Development: `https://dev.getgram.ai` (`values-dev.yaml`).
- Test: `https://test.getgram.ai` (`values-test.yaml`).
- PR previews: `https://pr-<number>.<environment>.getgram.ai` for both values (`infra/terraform/k8s/argocd.tf`).

These are same-origin HTTPS deployments, compatible with a host-only Strict refresh cookie. This is a source-configuration audit, not proof of the live cluster's effective values. Verify the rendered release and live routing at deployment time.

Local development uses HTTPS on the same `localhost` host with different dashboard/API ports. That is cross-origin but same-site: cookie matching ignores ports. Use `credentials: "include"`, exact dashboard Origin validation, credentialed CORS, and expose `Gram-Session`. A `localhost`/`127.0.0.1` mix is not interchangeable. The same host across worktrees can share cookies; use one worktree's matched URLs and expect a login if another worktree replaces its cookie.

If deployed site/API URLs ever differ, check both **schemeful same-site** and **host consistency**. CORS permission does not make a cross-site Strict cookie usable. A cross-site dashboard needs a same-site API proxy or an explicitly redesigned authentication contract; do not silently weaken SameSite or broaden Domain. Even two same-site subdomains cannot share this host-only cookie: login callback and refresh must use the same API host. Redirect aliases to the canonical host before login rather than setting a broad domain cookie.

## Verification and safe diagnostics

- Test from a freshly signed-in browser on the canonical host: refresh returns 204 with an access header, not HTML; no response body contains refresh credentials.
- Inspect cookie **attributes**, not values: both refresh copies have no Domain and have Secure/HttpOnly/Strict. Each auth RPC receives only its matching refresh cookie. Ordinary RPC and chat requests must not contain `gram_refresh`; logout must clear both copies.
- Confirm a request without the refresh cookie is unauthorized, a wrong/missing Origin is forbidden, and logout does not allow subsequent refresh. Confirm ordinary traffic cannot keep the original access token alive beyond its fixed expiry.
- Test idle wake-up, an active chat crossing access expiry, stream reconnection, multiple tabs, scope switching, logout, and a stale pre-cutover tab. Do not log tokens to compare them.
- The shared telemetry header recorder fully redacts Cookie, Set-Cookie, and Gram-Session case-insensitively, regardless of the caller's sensitivity flag. The outbound tool HTTP header allowlist also drops these headers. Standard HTTP request logging records safe URL/status metadata, not raw headers. Keep equivalent redaction at the load balancer, trace collectors, and any future debug middleware; do not enable full header capture for session endpoints.
- Keep `curl -v`, browser HARs, screenshots of cookie values, request dumps, and response-header dumps out of tickets and commits. Record only statuses, route/service names, cookie attributes, and sanitized errors.
