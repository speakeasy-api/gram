# Slack workspace authorization

Organization administrators manage workspace authorizations under Identity, in the Slack workspaces preview tab. Every connection, sync and member operation requires a browser session with `org:admin`; support sessions and API keys are refused. The shared Explore Demo organization is read-only: listing remains available, but begin, callback, and disconnect refuse the exact demo organization before consuming OAuth state, calling Slack, or changing connections. The retargeted local seed remains writable.

Reuse the Gram Slack app with `SLACK_CLIENT_ID` and the existing `SLACK_CLIENT_SECRET`. Both must belong to the same Slack app. Empty values and `unset` leave authorization unavailable. Register `<SERVER_URL>/rpc/slackDirectoryConnections.callback` with Slack. The server requires HTTPS outside local development. The directory authorization requests the bot scopes `users:read` and `users:read.email`. It accepts workspace installations, including a workspace within Enterprise Grid, and rejects organization-wide installations. OAuth exchange and `auth.test` must agree on the workspace ID.

Slack [adds scopes across installations of the same app](https://docs.slack.dev/authentication/installing-with-oauth/), so an existing installation may return a token with additional scopes. This service uses it only for directory access.

Credentials are encrypted together in a versioned bundle. Access tokens, refresh tokens, token type, and expiry remain server-side. Each sync refreshes a rotating token when it is within 30 minutes of expiry and stores the new bundle before using it, because Slack refresh tokens are single use. A rejected refresh requires reconnection; a transient failure retries. A token without a refresh token requires reconnection once it expires. A rate-limited refresh retries after Slack's Retry-After delay. No remote Slack app settings are changed by this implementation. Disconnect clears Gram's stored credentials; it does not uninstall the Slack app or change project runtime installations.

OAuth state lasts ten minutes and is bound to the organization, user, and session. Completion consumes it atomically. Connecting a listed workspace again, and disconnection, preserve the durable workspace row and replace its generation. Disconnect also deletes the workspace's synced members and resets its sync state, so connecting it again starts from a fresh sync. Each begin captures the visible generations so an authorization started before another administrator's disconnect cannot restore access. Concurrent first connections to the same workspace require the later completion to start again. Mutation and audit commit together.

Connected means authorization succeeded and its stored credentials have not expired. It does not claim a directory was synced or that invocations are protected. Complete syncs update observed memberships. Administrators can explicitly associate each retained membership with an existing active person in the same organization. External Slack Connect users are outside this version's scope.

## Platform MCP assessment

The outcome is browser consent for a specific organization's Slack workspace, performed by an organization administrator. Existing `attach_platform_mcp_identity_provider` manages project MCP sign-in provider attachment and does not represent this connection. The sync release adds directory inspection and refresh for the same organization administrator. No Platform MCP tool is added: these endpoints deliberately require a live browser session, and reject API keys and support sessions. External OAuth and managed-assistant actors cannot preserve that authentication contract. Existing identity-provider tools and shipped skills concern project MCP sign-in and remain unchanged. Endpoint boundary tests, generation checks, and publication tests establish the restricted outcome. A future agent-facing directory tool needs an explicit authorization contract.

## Local evidence

The shared demo/local seed contains two synthetic workspace history records without usable credentials. One is disconnected and one requires authorization. Seed screenshots do not establish a successful Slack OAuth exchange. Provider tests use a deterministic local HTTP server to verify the Slack protocol, including workspace mismatch, rejected scopes, enterprise installation, and rotating tokens. Live Slack verification additionally requires the app client ID, the existing secret and a registered callback.

## Directory sync

A successful connect or reconnect requests an initial sync after authorization commits. Administrators can also request a sync and inspect one workspace or search across all workspaces. A scheduling failure leaves authorization intact and the directory marked never synced or stale, with a manual retry available.

Shared Explore Demo refuses sync requests and activity execution.

One durable Temporal workflow runs per requested sync, deduplicated while running by task queue, connection and generation. One activity fetches every users.list page before publishing. A Postgres session advisory lock serializes the entire attempt, including provider waits, across workers and retries. It holds a dedicated pooled connection and publishes on that same session. Because that connection is held through provider waits, each worker process runs at most a quarter of its pool as concurrent syncs; the rest wait, still heartbeating, before taking a connection. The repository configures pgxpool directly; this requires a direct or session-pooled Postgres connection, not transaction pooling.

The activity fences its start and publication with the connection generation and workflow start timestamp. Disconnect, reconnect, superseded attempts and retries after a committed publication cannot overwrite a newer directory. Publication locks the connection, verifies usable credentials again, upserts in batches of 500, marks absent retained memberships unknown and records the successful generation in one audited transaction. Mapping rows and revisions are preserved. Publication locks all retained memberships before reading current mappings or writing review findings. Failed or partial fetches publish nothing. Manual sync audit metadata records observed members, excluded external observations and bots; scheduled syncs are not audited. The sweep backs off a workspace whose latest sync failed for six hours.

The provider follows Slack’s [users.list pagination](https://docs.slack.dev/reference/methods/users.list/) with 200 rows per page and honors [Retry-After](https://docs.slack.dev/apis/web-api/rate-limits/). It caps a fetch at 50,000 distinct observations and 10,000 pages, failing without publishing when either limit is exceeded. Duplicate users across pages use the latest observation. Slack pagination itself is not a point-in-time snapshot. A rate-limit delay that leaves less than 30 minutes for another attempt within the two-hour sync budget ends the sync as failed. The previous directory stays available and an administrator can retry later.

Only matching workspace IDs without stranger or conflicting profile-team evidence are imported, following [Slack Connect’s external-user rules](https://docs.slack.dev/apis/slack-connect/#determining-whether-a-user-is-external-must-be-done-implicitly). Enterprise identifiers alone are insufficient. Explicitly unconfirmed email addresses are omitted; no email creates a mapping. Missing profile fields and account state remain unknown. Bots and guests are labeled in the directory; bots and apps cannot be assigned to people.

Freshness comes from the last complete publication and its generation, independently of workflow progress. The UI shows the last full sync, observed member count, retained absent rows and bounded errors. Temporal status lookup has one shared two-second page budget and degrades to unknown. Progress reports pages and members, never a guessed percentage.

Temporal actions/month ≈ 2N + R + 2,880 + 2,880·W per namespace, where N is connects and manual syncs, R is activity retries and W is connected workspaces. A 30-minute schedule starts one sweep workflow and one activity per tick (2,880/month); the sweep starts the usual one-workflow, one-activity sync for each connected workspace whose last sync began more than 25 minutes earlier, oldest first and at most 100 per tick. A manual sync already running for the same generation is left alone. Timers and signals: 0. Scales with connected workspaces, not members or pages; 50 workspaces cost about 150,000 actions/month. PR previews in the dev namespace each register their own queue-scoped schedule.

## Admin identity mappings

The member table shows one row per synced workspace membership, with Slack name and email, workspace, directory state, Personnel and mapping status. Search, workspace and mapping-status filters apply across retained history. Clicking Personnel opens a current review of the membership and the existing organization people. Matching normalized email addresses label suggestions, including multiple candidates with the same address; they never select or confirm a person automatically. No person is created or merged.

Confirming a person, reassigning and choosing Not mapped require the same live browser session, `org:admin` and organization rollout as directory management. API keys, support sessions and employees cannot edit. The handler locks the membership, compares the submitted mapping revision and source-evidence token, and locks the target's active organization relationship and user with `LockActiveOrganizationUser`. Cross-organization, missing and inactive targets receive the same refusal. Email equality grants no authority.

Each accepted decision increments `mapping_revision` and records its actor and before/after snapshots atomically. The mapping UUID identifies a continuous assignment to an immutable person target. Reconfirmation of that same person keeps the UUID, advances the revision and clears the finding. Reassignment revokes the old row and inserts a new UUID; unmapping only revokes. Mapping, unmapping and mapping again cannot make an older dialog current. An attempt to remove an already-unmapped membership returns 409.

Sync records a review finding only on a currently mapped membership: a transition to bot/app or unknown account type; a transition to deactivated or unknown state; absence from a complete snapshot after previously observed presence; or a change between two known nonempty normalized email addresses. Changes in display name, email case or surrounding whitespace, and email appearing or disappearing do not raise findings. A Slack email different from the mapped person's email is not a conflict. The first finding and detection time remain until an admin decision, even after recovery or another finding. Current directory state remains visible alongside that earlier reason. Repeated absence after admin reconfirmation is not a new finding; a return followed by another absence is.

Publication takes all existing membership row locks in a separate statement before inspecting mappings. Later statements see committed admin decisions, and subsequent admin writers wait until publication commits. A fetch begun before confirmation can still publish new evidence and flag it for review. The opaque source token covers displayed profile, state, presence and finding evidence, excluding sync timestamps; changed evidence rejects an old dialog with 409, while an unchanged sync preserves the token.

Disconnect and Slack deactivation retain mappings. Admins may correct or remove them in stale history, including unknown memberships; bots/apps permit removal only. Association and source eligibility are separate. These operations grant no permissions, reassign no historical sessions and implement no invocation enforcement. DNO-1048 owns verification and runtime checks of the current revision, findings, active person, source eligibility and connection freshness. Reconfirmation does not invalidate UUID-bound authority by replacing a UUID.

Platform MCP assessment for mapping: this is an organization administrator's explicit association of a retained membership with a known person. Existing identity-provider tools concern project MCP sign-in, not personnel assignments. No tool is added because external OAuth and managed-assistant identities do not satisfy this feature's deliberate browser-session-only contract. The dashboard and management API preserve target selection, fresh evidence, revision checks and atomic audit. Boundary and lifecycle tests prove that contract; an agent-facing mapping workflow requires separately approved authorization semantics.
