Enterprise Managed Authorization is now its own section on a remote MCP server's settings page, below Identity, with one Turn on or Turn off action. It reads as a chain: the sign-in people use, the identity provider that vouches for them, what the service trusts (each identity provider's issuer URL, folded away once the service has accepted it anywhere in the organization), and the client, each linking to where it is changed. The section shows "Working" only once the service has accepted a sign-in for that server. It now also appears for an organization-level sign-in that Speakeasy's own issuer can vouch for, not only one that trusts an external identity provider. A project-level sign-in gets a notice that an organization-level one is needed.

Who vouches is derived rather than chosen per server: by default, each server is vouched for by whatever signs its people in. By default a service accepts every identity provider: a server whose sign-in trusts an external identity provider uses that provider alone, and a server whose sign-in trusts none uses the organization's Speakeasy issuer. Setting up Speakeasy never adds it behind an external provider, so nothing changes for existing integrations whose sign-in trusts an external identity provider. An admin can narrow which identity providers a service accepts (`organizationRemoteSessionIssuers.setEMAProviders`), for every server reaching the service. The API stores the providers as an ordered list, but each server uses only the provider its sign-in goes through, so the list acts as the set of accepted providers.

The organization's Identity providers tab gains a Services table, one row per service Enterprise Managed Authorization reaches, with a page per service for the once-per-service trust step and the identity providers the service accepts (a checkbox per provider, Save off with nothing checked, or go back to the default, which accepts every provider). The Speakeasy provider page lists the services that can use Speakeasy, split by whether each has accepted it. Each service page lists the MCP servers that reach the service, each linking to its Enterprise Managed Authorization settings, with its project and whether it is on and working, on but not proven yet, or needs attention; servers you can't read are counted, never named. These read the new `organizationRemoteSessionIssuers.listEMAServices` API: every vendor authorization server a binding or saved provider list names, with the organization-wide providers, when the vendor last accepted each exact provider anywhere in the organization, how many distinct live MCP servers reach it, and those servers filtered to the ones the caller has `mcp:read` on (`servers`, `hidden_server_count`). A server is matched to a binding by its URL or by the resource its cached protected resource document names. `readEMA` reports, per provider, the same organization-wide acceptance, and, for the binding, when the vendor last accepted an assertion for it from a provider the service currently accepts and that can vouch now, so moving a server to an unproven provider reads "On, not proven yet" again. Only credentials that still hold an access token count as acceptance: retiring or purging one never reads as a fresh acceptance, and its evidence goes with it. `setEMAProviders` takes an optional `expected_providers`; when the saved list no longer matches it, nothing is written and the request fails with conflict, and the editor uses it to stop a stale draft from restoring what another admin removed. Platform MCP guidance describes the default and which identity providers a service accepts.

On a server's settings, a binding on a client whose authorization server the server's metadata no longer names keeps a Turn off action, since that client can't be replaced while the binding holds it. A temporarily disabled or paused provider stays accepted with a note instead of blocking Save.

Speakeasy only vouches for servers that use Speakeasy's own sign-in. On a server whose sign-in goes through an external identity provider such as Okta, an accepted Speakeasy is skipped as `not_trusted_by_endpoint` instead of asking people to sign in again, which could never help. `listEMAServices` reports each server's sign-in identity provider (`sign_in_issuer_id`, `sign_in_issuer_name`). The service page's editor and Affected servers table, and the server's own settings, flag servers left with nobody to vouch because the service doesn't accept their identity provider, and say how to fix it.

The dashboard calls the feature Enterprise Managed Authorization everywhere people see it. "Identity chaining" stays only in code and API names.
