Identity chaining is now its own section on a remote MCP server's settings page, below Identity. It shows whether chaining is on and which sign-ins this server uses, with a single Turn on or Turn off action, and the step the vendor needs (trusting the issuer, with a copyable URL) until it is on. It has no scope list of its own, and the vendor-wide EMA provider order is no longer shown on the server. It now appears for an organization user session issuer that Speakeasy's own issuer can vouch for, not only one that trusts an external identity provider. A vendor's EMA providers are derived rather than chosen per server: with no saved order, identity chaining tries the server's trusted external identity provider first and then the organization's Speakeasy issuer when it has one, so setting up the Speakeasy issuer makes it a fallback for every server. The `organizationRemoteSessionIssuers.setEMAProviders` API still replaces that default with a saved order; the `addSpeakeasyEMAProvider` endpoint is gone. Platform MCP guidance describes the derived order. Each provider in a server's `readEMA` and `prepareEMA` response, and in the Platform MCP XAA readiness output, now carries `last_accepted_at`: when the vendor last accepted an assertion from that provider for the binding, from its newest live cached credential.

The server's Identity chaining section now reads as a chain: the sign-in people use, who vouches for them, what the service trusts (with each identity provider's issuer URL and when the service last accepted it), and the client, each linking to where it is changed. A project-level sign-in says identity chaining needs an organization-level one. The organization's Identity providers tab gains a Services table, one row per service identity chaining reaches, with a page per service that holds the once-per-service trust step and the provider order; the Speakeasy provider page lists the services that trust it. These read the new `organizationRemoteSessionIssuers.listEMAServices` API, which lists every vendor authorization server a binding or saved order names, with the organization-wide provider order, each provider's newest acceptance across every binding, and how many servers chain through it.

The dashboard calls the feature Enterprise Managed Authorization everywhere people see it: the server section, its toasts and dialogs, the Services pages and the Speakeasy provider page. "Identity chaining" stays only in code and API names.
