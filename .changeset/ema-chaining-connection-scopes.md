Turning identity chaining on now records the server connection's scopes on the binding: what an interactive sign-in through the selected client requests for that server (the client's scope, the resource's challenge or pinned scopes, or what the resource and its authorization server advertise). The set is recorded whole, sorted: identity chaining drops OpenID Connect scopes from its request, and when that leaves none it still rejects an ID-JAG naming a scope outside the recorded set. Existing bindings are unchanged until identity chaining is prepared again with prepareEMA. prepareEMA records its `scopes` only when the client is not linked to the user session issuer, no single remote MCP server signing in directly through that issuer serves the resource, or the connection names only OpenID Connect scopes while the request names others; they are still what a DCR registration asks for, and an ignored value no longer changes the binding's generation or audit history. With neither naming a scope, nothing is recorded and identity chaining requests no scope, as before. A gateway member qualified through a different sign-in issuer is not resolved, so its binding records the request's scopes. readEMA, prepareEMA and Platform MCP's get_xaa_readiness also report the connection's current scopes and whether they differ from the recorded ones, and the Okta resource connection view reports the recorded scopes for a bound server.
