Turning identity chaining on now records the server connection's scopes on the binding: what an interactive sign-in through the selected client requests for that server (the client's scope, the resource's challenge or pinned scopes, or what the resource and its authorization server advertise), without OpenID Connect scopes. Identity chaining keeps requesting exactly the recorded scopes, so existing bindings are unchanged until an administrator turns identity chaining on again. prepareEMA records its `scopes` only when the client is not linked to the user session issuer, no single remote MCP server serves the resource, or the connection names no scope; they are still what a DCR registration asks for, and an ignored value no longer changes the binding's generation or audit history. readEMA, prepareEMA and Platform MCP's get_xaa_readiness also report the connection's current scopes and whether they differ from the recorded ones, and the Okta resource connection view reports the recorded scopes for a bound server.
