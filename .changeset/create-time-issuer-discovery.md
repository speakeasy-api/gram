When an identity provider create includes `authorization_grant_profiles_supported`, which the dashboard and admin forms send only for drafts built from discovery, the server now runs discovery itself on project, organization, and global creates and through server identity configuration. If every value the form submitted (endpoints, `jwks_uri`, documentation URLs, supported scopes, grant types, response types, auth methods, and capability flags) still matches the served document and its `jwks_uri` returns a valid public key set, the provider is recorded as discovered and stores the advertised authorization grant profiles. Fields the form left empty are filled in from the document. Before this, such providers were left undiscovered and did not appear in the Okta Cross App Access table. Creates that omit the field skip discovery. A mismatch, an invalid key set, or a discovery failure is logged and does not block the create. Project-owned creates now reject a taken slug before contacting the provider. Supported lists are compared as sets, a document found at the origin root is not recorded when it contributes any member, and discovery plus key-set validation is capped at about five seconds. When a create is not recorded as discovered, the submitted grant profiles are dropped. Identity chaining now treats a provider as eligible only when its metadata was discovered, and reports an undiscovered provider as needing metadata rather than as unsupported. Changing a provider's issuer URL clears its grant profiles and discovery record until the next refresh, and resets every discovered endpoint and capability the same edit does not restate. Server identity configuration picks the registration method (CIMD, dynamic, or manual) from the submitted form, not from fields discovery filled in. Federated sign-in applies the RFC 8414 default (`client_secret_basic`) when the provider omits `token_endpoint_auth_methods_supported`; an explicitly empty list admits no method.
