ID-JAG exchanges now accept only clients that use a client ID metadata document and that the issuer's existing client admission allows in open or presets mode; disabled admits none, and an issuer in disabled mode no longer advertises the ID-JAG grant profile. Dynamically registered and other non-document clients get `unauthorized_client` before the assertion is used, and every client refusal on this grant is logged and counted as an ID-JAG rejection. On a shared authorization server, an ID-JAG token request that names no `resource` is routed by the assertion's `resource` claim, so Codex works against the organization gateway; an unreadable assertion, or a resource claim that names no MCP server of that authorization server, gets `invalid_grant`. When neither the request nor the assertion names a resource, the exchange goes to the organization gateway if it is turned on and signs users in through that authorization server, and is otherwise refused with `invalid_request` as before. `get_inbound_ema_trust` reports each issuer's admission mode, its custom client URLs and the preset clients, and explains what presets or disabled mode means for ID-JAG sign-in.
