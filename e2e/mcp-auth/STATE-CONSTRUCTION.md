# Auth-path fixture construction and limitations

The gap catalog is an agent assessment, not an oracle. A gap ID identifies a hypothesis/variant to examine, not a required failure. Test outcomes and the stage actually reached are recorded separately. Nothing in this document authorizes management API or SQL writes.

## Construction categories

- **UI-created browser fixture:** product configuration and credentials originate in actual dashboard/staff controls; protocol clients only perform real MCP/OAuth calls.
- **In-memory product contract:** synthetic query-result structs or memory stores are passed to real production decision/service functions. This is not browser, database selection, persistence, or worker execution evidence.
- **Persisted historical/adversarial state:** current UI construction is unestablished. A preserved fixture or separately authorized hand-built state may be needed. These states have not been inserted through SQL.
- **Environment/protocol prerequisite:** e.g. real native agent, HTTPS workload issuer, worker timing, or assistant/model runtime. A missing prerequisite is not evidence that hand-built database rows are necessary.

All browser scenarios require freshly verified persisted typed-client enforcement. An enforcement annotation alone does not prove a particular request avoided a compatibility hand-back.

## States that do not inherently require manual SQL

- G22 EMA/chained personal selection is an ordinary supported-type graph, not necessarily historical corruption. Browser execution needs a real supported identity/chained-token fixture; in-memory selection/permission evidence cannot stand in for its protocol exchange.
- **G23 correction from actual UI/source evidence:** `AddCredentialSheet.tsx` filters both new header-only methods and reusable static/pass-through clients when `tunneled` is true. All six direct/stored/project runtime variants stopped before credential creation; these are **UI construction blockers, not measured forwarding failures**. Exercising persisted runtime state currently needs a preserved tunnel/header association or separately authorized hand-built typed client/header/link rows. No such rows were created. The in-memory production tests independently exercise the `tunneled_headers_only` branch.
- G10/G16/G17/G27 need the actual headless/assistant/workload/profile surface. Issuance-profile UI choices, static agent keys, upstream client credentials, and assistant shell mounting are not interchangeable evidence.
- G15 public native tunnels intentionally do not borrow personal grants. A public-tunnel isolation test beside a live-then-dead personal grant does not automatically reproduce an anonymous-owned grant on a hosted public server. Construction and result must name the exact variant.
- G28 missing/expired consent inventory has a ten-minute TTL aligned with challenge state. Membership reduction is not automatically the same conflict condition: the measured stale tab returned an authorization-code redirect, so runtime access must be checked rather than assuming 409. A separate direct upstream-URL mutation exercises an access-relevant backend fingerprint. The exact cache-miss/expiry branch may need a controlled clock or missing cache entry; no cache state was manually changed.
- G26 is backend-only shadow characterization. It is not credited as typed browser serving or proof of shadow parity.

## SQL / identity safety

Local graph diagnostics remain bounded, project-scoped, repeatable-read and read-only. No tokens, header values or raw database identities are exported. New fixture captures share a random alias salt within one scenario so identity can be compared before/after mutations; aliases from different scenarios or historical captures must not be compared. The salt is not attached to reports. No production extracts are fixture inputs.
