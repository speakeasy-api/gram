## Mock sensitivity

The old mock advertised the same scopes everywhere and did not enforce token scopes on protected MCP requests. It could not detect the incident's issuer-default scope fallback. The updated mock rejects missing/wrong resource scope and records failed authorization attempts, including an omitted resource, without recording tokens, codes, state, redirect URIs or secret values. Unit tests validate that these faults are observable; only browser/protocol runs can establish product failures.

The first resource run encountered a helper gap: Reconnect was not recognized. That timeout is not counted as a product regression. The helper now drives the real Reconnect control. A later trace reached the provider with an omitted resource and issuer-default scopes; the assertion-based rerun now fails at the actual resource/scope contracts, as recorded below.

## Confirmed targeted red run

`mise run test:mcp-auth --grep 'shared registration keeps distinct resources|reused registration requests target resource scopes'` — **2 failed, 0 passed**, on unchanged product code, with persisted enforcement verified in both cases.

- **Resource case:** the same registration that successfully authorized A is used for B, but the authorization request has `resource: ""` instead of B's exact resource. The mock returns `invalid_target`; the test fails `TYPED_RESOURCE_REGRESSION`.
- **Scope case:** B advertises/requires `fixture:scoped`, but the actual request contains `[fixture:read, openid]`; the test fails `TYPED_SCOPE_REGRESSION`. This request also omits the resource. These are two observed contract failures in related topology, **not proof of two independent root causes**.
- The UI reread confirms exactly two servers on the same credential before either target login. A separate local read-only diagnostic confirms **both** fixtures have one enabled `remote_session` typed credential attached twice, distinct downstream issuers, a source issuer bridge, no target issuer bridge, and no direct target legacy association. Both also have NULL registration scope and NULL issuer scope override, with issuer defaults `[fixture:read, openid]`. The scoped failure is therefore not explained by an intentional client/operator scope pin. This verifies real missing-edge graphs rather than inferring them from the enforcement flag.
- Mock/driver unit checks: **20 passed**. E2E type-check: passed.

Evidence is ignored and local: `.logs/mcp-auth/incident-red.log`, `.logs/mcp-auth/incident-confirmed-red/` (preserved traces and redacted journals), and `.logs/mcp-auth/local-graphs.log`. The previous generic Reconnect-driver timeout and a form-readiness race are not counted as these product regressions.

## Gateway fixture correction through the dashboard

The earlier decryption blocker was a harness/environment mistake, not an unknown encryption issue. The pre-existing demo fixture stored plaintext while marking its header secret. Relying on that value violated the UI-setup requirement.

The local value was explicitly set through **MCP Settings → credential → Headers sent upstream → Save → Save on every server**. After a page reload, the credential editor was reopened and the stored secret was not echoed. No seed source change, direct SQL write, or API provisioning shortcut was used. Local UI evidence: `.logs/mcp-auth/ui-setup-save.log`.

The next gateway run no longer failed inventory/decryption; it reached `GATEWAY_FILTER_REGRESSION` (missing alpha fixture). That alone was not accepted as proof of the gateway bug: the follow-up run includes real direct consent and successful tool invocation for both alpha and beta before gateway authorization. **It fails `GATEWAY_FILTER_REGRESSION`: beta is absent from gateway discovery even though its direct-server grant and tool call succeeded.** Alpha is found. Persisted enforcement was verified. This is now a measured gateway discovery failure, not an inventory/decryption blocker. Evidence: `.logs/mcp-auth/gateway-ui-configured.log` and `.logs/mcp-auth/gateway-confirmed-red/`. This manual environment repair does not imply that the whole seeded organization is an isolated fixture; the new providers and grants are independently UI-created.
